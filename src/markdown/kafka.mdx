I'll skip explaining why Kafka is needed, since you probably already know. Instead, I'll focus on some fundamental details you might have missed.

## Three words you should know before using Kafka

- **Topic**: A named channel where data is sent and received.
- **Partition**: A topic is split into parts for better performance and scaling.
- **Offset**: The position number of each message in a partition.

Don't worry if you don't fully understand these concepts yet. I will explain them with easiest way I can.

<MdxImage src="/blog/kafka_1.png" alt="kafka_1" />

Ok, If this diagram is too complex for you, let's simplify it by my wording.

> Topic is like a folder, partition is like a file in that folder, and offset is like a line number in that file.  
> When you write to a topic, Kafka automatically chooses which partition (file) to write to, allowing parallel writes.  
> When you read from a topic, you can assign different partitions to multiple consumers, so they can read in parallel.

### Topic and Partition

Like I mentioned before, topic is like a folder, partition is like a file in that folder. When you create a topic, you can specify how many partitions (files) you want in that topic (folder).

- replica option : I will explain about replica in the next part (Kafka Cluster)
- time to retain data : how long do you want to keep the data in that topic before Kafka delete them automatically.
- max size : the maximum size for the entire topic before Kafka starts deleting old data automatically.

<MdxImage src="/blog/kafka_3.png" alt="kafka_3" />

You can create any topics with different partition numbers according to your need. More partitions provide several benefits:

**Consumer Side (Primary Benefit):** Increases parallelism. More partitions allow you to run more consumer instances (up to one per partition in a consumer group) simultaneously, which directly increases the rate at which messages can be processed.

**Producer Side (Indirect Benefit):** Increases write throughput. Producers can write messages to more partitions in parallel across multiple brokers, reducing the chance of a single partition or broker becoming a bottleneck.

### Start producing a message

To produce a message to a topic, there are three things you should know:

- **key (optional)**: The key's primary function is to enforce ordering and state management:
  - **Guaranteed Ordering (Consistency)**: If you produce five events for the same key, it ensures that all five events will be written to, and consumed from, a single, specific partition and the events will be processed in the exact sequence they were created.
  - \*\*\* If you leave the key as null (optional), the producer will distribute messages in a round-robin fashion across all partitions to ensure an even load. This is great for high throughput, but you lose the guarantee that related messages will be ordered.
- **value (required)**: The actual message content you want to send.
- **headers (optional)**: Additional metadata you can attach to the message (like HTTP headers).

> Normally, let Kafka choose the partition automatically unless you have a specific need.

And... If you go back to the topic overview page, you will see `__consumer_offsets`

> \_\_consumer_offsets is an internal topic that Kafka uses to store the offset information for each consumer group. This topic keeps track of which messages have been consumed by which consumer group, allowing consumers to resume from where they left off in case of failures or restarts.

I will create a consumer group by using golang to show you how it works.

```go
package main

import (
	"fmt"
	"os"
	"os/signal"
	"syscall"

	"github.com/confluentinc/confluent-kafka-go/v2/kafka"
)

func main() {
	conf := kafka.ConfigMap{
		"bootstrap.servers": "localhost:9092",
		"group.id":          "my-golang-consumer-group",
		"auto.offset.reset": "earliest",
	}

	topic := "user.activity.page-view.v1"

	consumer, err := kafka.NewConsumer(&conf)
	if err != nil {
		fmt.Printf("Failed to create consumer: %s\n", err)
		os.Exit(1)
	}
	defer consumer.Close()

	err = consumer.SubscribeTopics([]string{topic}, nil)
	if err != nil {
		fmt.Printf("Failed to subscribe to topic %s: %s\n", topic, err)
		os.Exit(1)
	}

	fmt.Printf("Consumer started. Subscribed to topic: %s. Waiting for messages...\n", topic)

	sigchan := make(chan os.Signal, 1)
	signal.Notify(sigchan, syscall.SIGINT, syscall.SIGTERM)

	run := true
	for run == true {
		select {
		case sig := <-sigchan:
			fmt.Printf("\nCaught signal %v: Terminating\n", sig)
			run = false
		default:
			ev := consumer.Poll(100)
			if ev == nil {
				continue
			}

			switch e := ev.(type) {
			case *kafka.Message:
				key := string(e.Key)
				value := string(e.Value)

				fmt.Println("-------------------------------------------------------")
				fmt.Printf("✅ Received message:\n")
				fmt.Printf("   Topic: %s | Partition: %d | Offset: %d\n", *e.TopicPartition.Topic, e.TopicPartition.Partition, e.TopicPartition.Offset)
				fmt.Printf("   Key: %s | Value: %s\n", key, value)
				fmt.Println("-------------------------------------------------------")

			case kafka.Error:
				// Error
				fmt.Fprintf(os.Stderr, "Error: %v\n", e)

			default:
			}
		}
	}
}
```

I run this code and consume some messages from the topic `user.activity.page-view.v1`. After that, I close the program and send a new message.

See what shows in the console log.

<MdxImage src="/blog/kafka_7.png" alt="kafka_7" />

You can see that when I run the consumer the second time, it starts consuming from the offset where it left off, not from the beginning. This is because Kafka tracks the offsets for each consumer group in the `__consumer_offsets` topic, allowing consumers to resume from their last committed position.
